Delivery Factory · Reference

How the delivery core works.

A work item goes in, a pull request comes out. This page explains the machinery in between: what is plain code, where a model is needed, what one run does step by step, and how a platform plugs in without the core knowing its name. Repo: github.com/agenticDraft/plugins

Built as plugins

Six Claude Code plugins. agentic-core drives the route and names no product. One platform pack, agentic-eds, says what each stage means for an Edge Delivery project. Four provider packs each fill one role: agentic-jira (tracker), agentic-github (scm), agentic-figma (design), agentic-playwright (browser).

Part one

The core

Everything in this part holds for any platform. The core defines the stages, the roles and the shapes; it never names a tracker, a design tool or a framework.

What it is

One command per ticket

The starting point was a checklist done by hand, and the quality bar lived in a document, not in the loop.

A developer read the ticket, wrote the block, started the local preview, compared the page against a design screenshot by eye, opened a pull request and pasted a screenshot back into the ticket. Done by hand, that is a checklist. Done by one long prompt, it drifts: the agent re-does work, carries every file it ever read, and nobody can say which step decided what.

The core replaces it with one command, /agentic-core:run-route <item>. It reads the item, plans, builds, renders, compares against the design, lints, and stops for a human at the decisions that matter. The run is a fixed route of fifteen stages. Each stage runs as its own isolated agent and reports back in five lines.

The core sequences, spawns, reads one verdict and branches. Everything that names a platform or a product lives in a pack.

Three layers

Where determinism stops

The core is not one program. It is three layers with a sharp division of work, and the useful thing to know is exactly where a model is needed.

Layer 1 · Scripts

No model, no tokens. Input is a file, output is one line and an exit code. Each script has a .test.sh beside it, so CI can prove this layer.

101 scripts in agentic-core/shared/lib/. The driver names 35 of them, two of which run as its own hooks; the stages call the rest.

instructions-stamp · check-preflight · check-credentials · check-run-state · evaluate-stage-conditions · reset-envelope · capture-envelope · run-stage · validate-result-envelope · write-run-state · check-tree-unchanged · derive-branch-name · handle-question · resolve-terminal-state …

Layer 2 · Contracts

Markdown files that define a shape once. Everything else points at them with one line instead of restating them, because a restated rule quietly starts to disagree with itself.

33 contracts in agentic-core/shared/.

result-envelope · stage-runner · terminal-states · question-protocol · error-handling · fix-loop · gate-contract · pre-flight · pack-manifest · role-operations · fact-record · run-state · external-content-safety · route-policy …

Layer 3 · The route driver

One skill, agentic-core:run-route. It owns control flow and nothing else, and it is the only component allowed to spawn a stage.

It never opens a source file or a path a stage wrote. A PreToolUse hook on Read enforces that while a run is live. Before anything else it proves its own instructions are the copy on disk, so a stale copy cannot run a route with a step missing.

skills/run-route/SKILL.md · scripts/check-driver-read.sh

The one step that needs a model. Resolving a stage, validating its envelope and choosing the next move are scripts. Spawning the stage as an isolated subagent is not, so the script stops right there and says so about itself:

It does not spawn the adapter itself — that is the one step above this script that genuinely needs a model, left to whichever skill drives a full route.
— shared/lib/run-stage.sh

Two hosts, one driver

Interactive: a person types /agentic-core:run-route <item> [autonomous]. The skill sets disable-model-invocation: true, so a model never starts a run on its own.

Headless: a CI workflow in the consuming project runs shared/runner/route-agent.mjs. It adds guardrails, not orchestration: dontAsk permissions, a tool allowlist, forbidden-tool rules enforced twice, a write-protected plugin directory, a locked network allowlist, and caps on turns, time and budget. Both hosts run the same driver, the same stages and the same run files.

Four roles and their operations

Where the work item lives.fetch_item · post_note · attach_file · list_types · create_item · update_item

Where the change is published.create_branch · publish_change · check_status
design
Where the design reference comes from.fetch_reference

What renders and measures the page.render · capture · measure · interact

A stage calls an operation by role, never by pack name. Project config binds each role to one provider pack, and the pack is found by its plugin name through a registry each plugin writes at session start, never by a relative folder path.

The result envelope

## Result
verdict: pass | warn | fail | question
summary: <one sentence>
artifacts:
  - <path written or updated>
next_action: <short phrase, or "none">
# on fail or question:
error_class: TRANSIENT | VALIDATION | PERMANENT
# on question:
question: …   blocker: …   options: …

Every stage and every role operation ends with this block. It must be the last thing emitted; the driver reads nothing else.

Verdicts

pass
Go to the next stage.
warn
Go on; the warning is recorded. Never terminal.
fail
The run ends. The driver never retries.
question
Asked at the stage boundary only. Interactive: a person answers and the stage runs once more. Autonomous: the blocker is posted to the item and the run ends blocked.

error_class

TRANSIENT
The environment is busy: a timeout, a quota. Ends blocked with the remedy.
PERMANENT
The environment is missing something: a tool, a login. Ends blocked with the remedy.
VALIDATION
The input itself was wrong. The verdict decides: fail ends failed.

A stage that fans out to subagents of its own uses a second block, ## Outcome with status: success | warning | failure. It shares no word with the envelope, so a block from the wrong tier fails validation instead of silently matching a branch.

Gates and terminal states

Three gates, three endings

Gates are ordinary stages to the driver. What makes them gates is what runs inside and what they may write.

readiness, plan-gate and publish-gate are the three gates. Inside each, the order is fixed: deterministic criteria scripts first, then a reviewing model only on what survives, on a stronger model tier. readiness writes nothing. The two reviewing gates write exactly two files, their findings report and their envelope. The driver snapshots the project tree before a gate and compares after; any other change ends the stage failed, whatever the envelope says.

delivered

deliver returned pass.

Prints the status table and the published location.

blocked

A question unanswered or posted back, a pre-flight or credential failure, a dirty tree at a fresh start, work already on the base branch, or an environment fault.

Prints what is missing and where it was recorded.

failed

A stage returned fail, or a contract violation: an envelope that does not validate, a stage that cannot be resolved, a gate that changed the tree.

Prints the failing stage and its summary.

Exactly one of the three ends every run. warn is never one of them.

Rejected alternatives

Shapes it was measured against

Kept because the reasoning behind a rejection is what nobody reconstructs later.

  • Wrong layer

    A shell loop as the orchestrator

    A script calling run-stage.sh in a loop. But run-stage.sh does not spawn the stage, on purpose. The loop would validate envelope files nobody had written and would "pass" having done nothing. The driver has to spawn a subagent, and only a skill can.

  • Conflicts with pre-flight

    A liveness probe instead of a declaration

    Pre-flight would prove a capability by calling it: start the tool, see whether something answers. A false negative there aborts a run before a branch exists, on sandbox or network conditions the pack author does not control, and a tool that answered once has not shown it is configured.

    So pre-flight reads what each pack declares. A provider pack lists its local preconditions with a probe and a remedy, the read-only health skill runs those probes on demand, and the operation itself refuses to run without its tool.

  • Duplicate state

    A second state file and a second progress file

    Both already exist: run-state.json and progress.md, with the two-hour resume window and a refresh after every stage. Two files for one state is a source of divergence, not redundancy.

Part two

A platform pack: agentic-eds

One worked example of how a platform binds the core's stages. Everything in this part is the pack's, not the core's.

EDS is one swappable platform pack. The core has a closed list of fifteen stages; a pack implements or declines each one and never adds a new one (D42). A React or Next.js pack could bind the same stages its own way tomorrow, with no change to the core. Behaviour no stage id covers goes inside a stage the pack already owns.

The default route

Fifteen stages, four of them conditional

From agentic-eds/pack.yaml. A filtered list, not a branching graph: conditions are checked once, after intake, and a skipped stage passes control to the next in list order.

Gate reviewer agent

Both reviewing gates, eds-plan-gate and eds-publish-gate, run as agentic-eds:eds-gate-reviewer: model: opus, effort: high, isolation: worktree, tools Read, Glob, Grep, Bash, Write.

It reviews, it never fixes, and it writes exactly two files. Because the harness may run it without the worktree, the gate checks its own isolation (check-gate-isolation.sh) and records present or absent in its report. It never changes the verdict; the driver's tree snapshot is what holds the two-file rule either way.

Conventions subagents

eds-conventions learns the project before anything is written. It dispatches three subagents of its own, styles, markup and component reuse, and synthesizes one conventions artifact.

The subagents answer with the inner ## Outcome block; the stage reports its own envelope and never passes a subagent's outcome through unchanged.

Edit budgets

A fix_attempts value is a budget of edits, declared only on a stage that asks check-fix-budget.sh before each edit.

  • verify-design · 2 edits
  • plan · 1 edit
  • lint · 3 edits

Any other stage uses limits.fix_attempts_default from project config.

Read from agentic-core 0.2.18 and agentic-eds 0.2.14 on main: the driver skill, shared/, pack.yaml and route.dot. Counts are file counts in those folders.
